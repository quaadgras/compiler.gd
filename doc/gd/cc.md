# C in Go: cmd/cc

`cmd/cc` translates a subset of C to Go so that C and Go share one
heap, one stack, one collector and one pointer representation, and C
cannot break what Go relies on. It is a prototype of the memory rules,
not of the compiler: it emits Go source that the existing toolchain
compiles. The generated Go imports `internal/c23`, the run-time support:
an internal package, which `cmd/go` lets only the packages it builds with
cc, and files that start with cc's `// Code generated by cmd/cc` header,
import (cmd/go/internal/load/c23_gd.go).

Like the fork's other tools, cc is an importable package: `cmd/cc/host`
runs it in-process (`Run`, `Translate`, `Package`), and the logic is in
`cmd/cc/internal/ccmain`, with no package-level state. It is part of the
go binary: `go tool cc` runs it in-process, with no binary in the tool
directory.

Each file of a command line is a translation unit. The units are parsed
several at a time, since nothing of one is another's until they are
linked; they are then linked and generated as one Go file, which is the
same whatever the order they were parsed in.

`cc -cache dir` keeps the translation of a command line in `dir`, with
what it read: the files, by their contents, and the files it looked for
and did not find (a header that appears in a directory searched before
the one that has it makes another translation). The same command line,
by the same cc, when all of that is as it was, gives the same Go without
translating. The cache is of a whole command line, not of each unit: the
units are linked as trees, so a unit has no Go of its own to keep, and a
change to one file translates them all. (When `cmd/go` builds a package
with cc, the translation is part of the package's build, which `cmd/go`
caches.)

## Where this stands (2026-11-25): the translation is 1:1

Most of this document describes C's pointers as typed capabilities
(`c23.Ptr`: a base, a size, a type and an offset, checked at every
access). That was removed on 2026-11-24: on a benchmark of what Godot's
core does it ran 1.5 to 9.8 times slower than `gcc -O2`, and the Go
compiler now checks `unsafe.Pointer` itself (unsafe.md). The sections
below that speak of capabilities, tagged words, side tables, split
words and faults describe what was, and are to be rewritten. What is
there now is one translation, in which C's objects and pointers are
Go's:

```c
static const char *name(enum color c) {
	switch (c) {
	case RED:
		return "red";
	case GREEN:
	case BLUE:
		return "green or blue";
	default:
		return "?";
	}
}
```

```go
func c0_name(c c23.UInt) *c23.Char {
	switch c {
	case 0:
		return c23.String("red")
	case 5, 6:
		return c23.String("green or blue")
	default:
		return c23.String("?")
	}
}
```

- **A C object is a Go variable** of the Go type that mirrors it (the
  struct, field for field), declared where C declares it, with C's
  name. A load, a store or a member's access is Go's own: `n->count++`
  is `n.count++`. An element of an array that is named (`a[i]`, not
  `p[i]`) is Go's index, with Go's bounds check. What the translation
  adds has names that begin with two underscores (`__1`), which C keeps
  for the implementation.
- **A C pointer is a Go pointer.** `*T` where C's type says what it
  points to; `*c23.Void` (`type Void [0]byte`, as cgo's) for `void *`,
  for a pointer to a function or to a type that is not complete, in C's
  library, whose functions take any pointer, in a call through a pointer
  to a function, and in variable arguments. One is converted to the
  other through `unsafe.Pointer`, and arithmetic is `unsafe.Add`: that
  is where the compiler checks, and the only use of `unsafe` in the
  generated Go.
- **C's types** have their C names: `c23.Int`, `c23.Long`, `c23.Char`,
  `c23.Double`, aliases of the Go types of their sizes.
- **Initializers** are in the declarations where they are constant:
  `int table[N] = {1, 2, 3}` is `var g_table = [8]c23.Int{1, 2, 3}`, at
  the package's level for a global and in the function for a local. A
  string literal is `c23.String("hello")`: the Go string's bytes, which
  the compiler ends with a 0.
- **Structs** are passed by the pointer to them and returned in memory
  the caller gives, as C++'s lowering expects (cxx.md).
- **Pointers to functions** point to a descriptor (`c23.Func`). A call
  through one passes every pointer as a `*c23.Void`: C and C++ call
  functions whose types differ in what their pointers point to (a
  virtual function's `this`), which to Go are different types.
- **malloc** converted to a pointer to a type that has pointers is a Go
  allocation of that type. Otherwise it is memory in which every word
  may hold a pointer (`c23.AllocRaw`), which the collector looks at word
  by word. It is to become an allocation in spans of C's own, whose
  words all start as possible pointers, with a bit for each that a
  scalar store clears and a pointer store sets again, under a seqlock
  of the span taken only when a bit changes. `free` does nothing.
- **A union** (and a struct that Go cannot lay out as C does: packed,
  over-aligned) is its bytes to Go; its words, each a possible pointer,
  if a member is a pointer, so that the collector sees what C stores.
- **What Go has no variable for** is reached through its address, with
  internal/c23's loads and stores: bit-fields, `_Atomic`, `long double`
  and `_Complex` in memory, `va_arg`. A variable length array and a
  variable aligned more than Go aligns (`alignas(64)`) are allocated,
  and their Go variables are the pointers to them.
- **internal/c23 checks nothing.** `c23.Add`, `c23.Load32`,
  `c23.Memmove` are plain operations on a `*c23.Void`. The package is
  compiled without the compiler's checks, as the runtime is.
- **Speed.** On that benchmark (a sorted vector of structs, a tree, a
  hash map with string keys, byte strings), against `gcc -O2`: 0.85 to
  1.3 times with `-d=checkptr=0`. With the checks as they are today it
  is 0.9 to 10 times: each arithmetic and conversion is a call into the
  runtime. The typed code, which is most of C and C++, is at Go's speed
  either way; making the checks of the rest cheap is the compiler's work.

Where C and Go's rules for pointers disagree:

- **One past the end.** C lets a program make the pointer one past the
  end of an object and keep it. To Go that is a pointer to the next
  object of the heap: the check of pointer arithmetic refuses it, the
  collector would keep the wrong object alive for it, and stops if
  that one is free. So every object of C's on the heap has at least a
  byte after it: malloc and new allocate one more element (or word),
  and in a package that imports internal/c23 the compiler allocates a
  variable that it moves to the heap as `struct { v T; _ byte }`
  (cmd/compile's `ir.CObjType`), as Go itself does for a struct that
  ends in a field of no size. The stack, and the program's data, are
  each one allocation to both. Such a package is also compiled without
  the escape bits (`-d=gdescbitsoff`), which move a variable from the
  stack to the heap when a callee keeps its address: C has pointers to
  it where the compiler sees none. `new T[n]` of a class with a
  destructor keeps n in front of the array, as other compilers do,
  since the size of the allocation no longer says it.
  A typed pointer to the end (`T *end = a + n`) is a conversion to
  `*T` of a pointer that no T fits at. In such a package the
  conversion is checked by `runtime.checkptrAlignmentC`, which lets a
  pointer into an object of the heap be if its type reaches past the
  object's end. This is the one place where C is checked less than Go:
  a load or a store through such a pointer reaches up to one value
  past the end, and nothing stops it. C's spans (above) would know the
  size that was asked for, and with it the end exactly.
- **Integers in pointers.** C keeps them there (`SIG_IGN`, `(void *)1`,
  a union's `int`) and adds to a null pointer. Such a conversion goes
  through `c23.FromInt`, unchecked; a pointer to a function is a
  `*c23.Void` because of them; and a program with C in it runs as with
  `GODEBUG=invalidptr=0` (`runtime.c23AllowIntegers`), which also lets
  pointer arithmetic give a small integer.

Not there: wasm. The translation does not build for `GOARCH=wasm` yet
(the library's 1:1 entry points take 64-bit sizes, and `GOWASM=gc`'s
runtime lacks two of internal/c23's hooks), where the older one ran
`TestInterop`.

`CCDEBUG=layout` (or `cc -debug`) adds to the generated Go the
declarations that fail to compile if Go lays a struct out other than C
does; the tests set it.

## cgo packages, with cgo off

Go code uses C through cgo's `import "C"`, unchanged. When cgo is off
(`CGO_ENABLED=0`, or a target with no C toolchain, such as wasm), go
build compiles a package that imports "C" with cc instead, if it can:
if every preamble and C file of the package, loaded as cgo would load
it, has no `#cgo` directive and includes only headers cc provides
(`<stdio.h>`, `<stdlib.h>`, `<string.h>`, `<stdint.h>`, `<stddef.h>`,
`<assert.h>`) or the package's own (`"..."`), and the package has no
C++, Objective-C, Fortran or assembly for a C compiler. Such a package
is loaded again as if cgo were on: its import "C" files and its files
with a `cgo` build constraint are in, its `!cgo` files out, as with cgo
(`ccContext`). Any other package that imports "C" builds as before,
without its cgo files. No package of std or cmd is built by cc.

The build (cmd/go/internal/work/cc_gd.go) runs cc in-process on the
preambles and the C files, as one unit, and rewrites the import "C"
files as cgo rewrites them (`rewrite.go`), into the object directory:

- `C.f(args)` calls the translation of f, with the arguments as they
  are: C's types are the Go types that mirror them and its pointers are
  Go's. `void *` is `*c23.Void` in the translation and
  `unsafe.Pointer` to Go, as with cgo: an argument is converted from it
  and a result to it.
- `C.struct_node`, `C.union_value`, typedefs, `C.int` and the other
  basic types are the mirror types; enum constants are their values; C's
  globals are the Go variables they are translated to; `C.CString`,
  `C.GoString`, `C.malloc` and `C.free` work as in cgo. A field that is
  a `void *` is a `*c23.Void` to Go, not an `unsafe.Pointer`.
- Every name cc generates starts with `_C23`, so nothing clashes with the
  package's own.
- A function with variable arguments, and one that takes or returns a
  struct by value, cannot be called from Go.

`testdata/interop` is such a package: lists that each side allocates and
the other walks, a slice kept by C, strings, variables, enumerations,
unions, memory that malloc was given no type for, and arrays summed
from one past their end, across collections (`TestInterop`).

## What Go may rely on, with no checks

Plain Go code that uses C's memory through the generated mirror types
(`C.struct_node` for C's `struct node`), or that hands C its own memory,
may assume what it assumes of any Go memory:

- a word Go reads as a `*T` is nil, a pointer to a whole live `T`, or a
  word that faults (tagged, below);
- C never writes a word of a Go value with invariants (a `bool`, a string
  or slice header, an interface, map, chan or func), never writes an
  integer over a pointer word, and never writes outside what Go gave it.

C pays for all of it. Go pays nothing, and nothing has to be pinned or
kept on the heap for C's sake.

## The rules

**A C pointer in a register** is `c23.Ptr{obj, size, off, ti}`: a
capability (the base, size and type of the memory it may reach) and an
offset, which may be anything. Arithmetic is never checked. Every access
is checked against the capability and its type.

**A C pointer in memory** is one word where the memory's type has a
pointer. If its address holds a whole value of the type the word points
to, the word is the address: a Go pointer. Otherwise (out of bounds, or
of the wrong type: an `int *` stored in a `struct node *` field) it is
the address with bit 55 set: not canonical, so it faults wherever Go
dereferences it, and the collector does not take it for a pointer. Its
capability is kept in a side table, so C can still use it as what it is.

**Capabilities come from types, never from the heap's guesses:**

- *C's objects* (`malloc`, globals, locals) begin with a header holding
  their type and exact size. A word that points into one gets the whole
  object back (`runtime.c23Object` finds the object; the header is
  trusted only if its type descriptor is a registered one, which safe Go
  code cannot forge).
- *Go's pointers* get the capability of their static type, as cgo's rules
  say what C may reach: the value `*p` for `C.f(p)`, the whole array for
  `C.f(&x[i])`.
- *A word loaded from Go's memory* gets the capability of the type the
  memory says it points to: a `*T` field gives one `T`. Go's own
  invariant makes that exact.
- *A capability a word cannot give back* (a slice's array stored in an
  `int *`, an out-of-bounds pointer) is kept in a side table, wherever
  the word is, so a pointer C stores anywhere comes back with the
  capability it had. An entry is used only while its word still holds
  what was stored with it, so a stale entry can only give back a
  capability C once had for that exact word. The tables
  (`internal/c23/side.go`):
  - *in C's object*: in its header, by the word's offset, so it moves
    with the object (on the stack too) and dies with it;
  - *in a goroutine's stack*: in the goroutine (`g.c23`), by address.
    `copystack` re-keys it when the stack moves (every address shifts by
    the same delta), entries of returned frames are dropped as new ones
    are made, and `gdestroy` drops the table;
  - *in Go's heap*: by the object, removed by a cleanup when the object
    dies;
  - *in Go's globals*: by address.

**Stores keep Go's invariant**, and each decides from its own operands
only, so no check races with another thread:

- a scalar store may not write a pointer word or a word of a Go value
  with invariants;
- a pointer store may only write a pointer word, and stores a plain
  address only if the target holds a whole value of the pointee type
  (the same type, or for a type without pointers, bytes without any);
- a pointer made of an integer has no capability: it can be passed around
  and compared, not dereferenced. `intptr_t` and `uintptr_t` are the
  exception: they are integers that carry a pointer's capability, as CHERI
  C's `__intcap` types are (internal/c23's `intcap.go`), so a pointer
  converted to one and back is the pointer, checked as ever. Arithmetic is
  on the address and keeps the capability; in memory one is a split word,
  the address in its bytes and the capability in the side table.

**Types, not the heap, answer every check**, so C's objects and Go's may
be on the stack. Each C local is a Go variable of type `c23.Obj[T]`;
escape analysis keeps it on the stack unless C stores its address
(`StorePtr` makes what it stores escape), exactly as it does for Go. A
Go caller's stack variables passed to C stay on the stack too: the demo
measures no allocations for either.

**`free` frees nothing.** The collector frees what is no longer
reachable, and a capability keeps its object reachable, so no capability
is ever revoked: a use after free sees the object as it was, never
memory reused for another (CHERI needs quarantine and revocation sweeps
for that guarantee). Revoking on free would need the bounds in the
object, read by every access, as Fil-C keeps them; ours travel in the
`Ptr`. `free` and `realloc` fault for a pointer `malloc` cannot have
returned: one into an object rather than to its start, one to Go's
memory, or one to an object that is not an allocation of its own (a
local on the stack). A pointer with no capability may be `malloc`'s
result that went through a `long`: `free` lets it be, and `realloc`,
which cannot copy its object, faults.

## Unions and untyped memory

Go sees a union as its bytes, as cgo makes it (`type union_value struct
{ _ [0]uint64; b [8]byte }`, aligned as the union is). C's untyped
memory (`malloc` into a `char *` or `void *`, which placement `new`
carves objects out of) is bytes too (`c23.Raw`). Their words are *split*
words:

- to Go and the collector they are scalars, so Go reads and copies them
  freely and no union can hand Go a pointer;
- C may store pointers in them: the capability goes in the side table
  first, so that what it points to stays alive, then the address as
  bytes;
- a pointer C loads from a split word gets the capability kept for the
  word whatever the bytes hold now, as in Fil-C, and every access is
  checked against it: after a `double` is stored over a pointer, reading
  the union as the pointer gives an address far outside the old object.

Objects that C places in untyped memory work fully in C, with pointers
between them; Go sees them only as bytes (a `*struct_node` into a pool
comes back tagged), which is cgo's rule too.

## Escape analysis and the Ptr

Escape analysis sees a `Ptr` as one value: if anything reachable from it
leaks, so does everything its memory points to. So a `Ptr` holds its type
descriptor as an integer (descriptors live for ever), and fault messages
are built from the type alone; otherwise every check would move what C's
and Go's stack values point to into the heap.

## On wasm

The same package runs on wasm (`go test cmd/cc` runs the interop test on
each, with node):

- **GOWASM=linear** (Go's own port; what wasip1 means): Go's runtime, so
  the same hooks. Addresses are 32 bits, and a load keeps only those, so
  a tagged word would reach memory: the compiler's explicit nil checks on
  wasm also stop a pointer of 1<<32 or more
  (`OpWasmLoweredNilCheck`), so Go's use of a tagged word is a nil
  dereference panic, which it can recover from (better than native,
  where it is a fault).
- **GOWASM=gc,split** (what js means): every value has an address in
  linear memory and every pointer its block's array of pointers, so
  `runtime.c23Object` is the block's base, with no lookup
  (runtime/wasmgc/c23.go), and stacks never move, so no table needs
  re-keying. `internal/c23` never makes a pointer of an integer there (a
  pointer made of an integer has no array of pointers): a capability's
  type is an index (`tinfoTab`), not a pointer, and `noescape` is the
  pointer itself. Addresses are under 1<<31, so the tag is bit 31: a
  tagged word is past the end of memory, and Go's use of it traps (the
  program stops; it cannot recover).
- **GOWASM=gc** without split has no addresses: cmd/go does not build a
  package with cc there, as if it could not.

## C on wasm32

`GOOS=js GOARCH=wasm` (`GOWASM=gc,split`) has 4-byte pointers, `int`
and `uintptr` (wasm-gc.md, stage 16), and C compiled by cmd/cc there has
clang's `--target=wasm32` data model, so that a C struct and the Go
struct that mirrors it (`C.struct_node`) have the same layout.

**Where it is chosen.** `cmd/cc/internal/ccmain/target.go`, once for the
process, from the word size of the target as `internal/buildcfg` gives
it to every tool (`GOWASM.PtrSize()`): ILP32 for wasm with 4-byte words,
LP64 for everything else (native targets, `GOWASM=linear`,
`GOWASM=gc,split,ptr64`), exactly as before: cc's output for basic.c,
libc.c, slimcc's and c-testsuite's tests, Lua and SQLite is byte for
byte what it was natively and for linear and ptr64. The size of a
pointer and of `long` are two fields (`ptrSize`, `longSize`); the type
of an address in the generated Go is `uintptr` whatever they are. The go
command runs cc in-process, so cc sees the target only through the
environment: `go build` refuses to build C with cc for a GOOS/GOARCH set
in a go env file instead (`cc_gd.go`), which compile and link handle by
running out of process.

**The data model** (checked against clang 21: `bench/wasmgc/cclayout`,
116 sizes, alignments and offsets of 21 structs and unions, and Go's
layout of the 11 that Go can declare):

| type | LP64 | wasm32 |
|------|------|--------|
| `char`, `short`, `int`, `float` | 1, 2, 4, 4 | the same |
| `long`, `unsigned long` | 8 (Go `int64`) | **4 (Go `int32`, `uint32`)** |
| pointers, `nullptr_t`, `va_list` | 8 | **4** |
| `size_t`, `ptrdiff_t` | `long`: 8 | `long`: **4** |
| `intptr_t`, `uintptr_t` | `__intcap`: a pointer's, 8 | **4** |
| `long long`, `double` | 8, aligned 8 | 8, aligned 8 (as Go's `int64`) |
| `int64_t`, `intmax_t`, `int_least64_t`, `int_fast64_t` | `long` | `long long` |
| `int_fast16_t`, `int_fast32_t` | `long` | `int` (musl's, wasi-libc's) |
| `long double` | 16, aligned 16, a double's value | the same (clang: fp128) |
| `__int128`, `_Complex double` | 16/16, 16/8 | the same |
| `wchar_t`, enums | 4 | 4; an enum wider than 32 bits is `long long` |
| `max_align_t` | `long` | `struct { long long; long double; }`: 32, aligned 16, as clang's |

C's `long` is Go's `int32` on wasm32, as cgo's `C.long` is on a 32-bit
target (cgo's is a distinct type of that size; here it is `int32`
itself, as `C.long` was `int64` itself before). Integer constants get
C's types for a 32-bit `long` (`3000000000` is `long long`), constant
folding wraps at 32 bits, `__builtin_clzl` and the others with `l` work
on 32 bits, `__builtin_bswap64` on `unsigned long long`; the predefined
macros are clang's for wasm32 (`__ILP32__`, `__SIZEOF_LONG__ 4`, ...)
and `inttypes.h`'s formats follow (`PRId64` is `"lld"`).

**The C library's types** that clang cannot give without a libc are
wasi-libc's and musl's on 32 bits: `time_t`, `clock_t`, `off_t`,
`blkcnt_t`, `suseconds_t` of 64 bits, `dev_t`, `ino_t`, `nlink_t` of 64;
`ssize_t`, `blksize_t`, `pthread_t` and `tv_nsec` stay `long`. With
these, `struct stat`, `struct timespec` and `struct timeval` keep LP64's
offsets (a 4-byte `long` and padding where LP64 has 8 bytes);
`struct rusage`'s 14 `long`s, `struct passwd`'s pointers, `struct
lconv`, `ldiv_t` and `argv` are laid out by the model. The headers stay
written for LP64; `target.go` edits their text for ILP32 (`ilp32Headers`,
each edit checked to apply).

**The library's Go keeps LP64's types**: `c23.Strlen` returns `uint64`
everywhere, and a call from wasm32 C converts a `long` or `size_t`
argument to `int64`/`uint64` and the result back (`libcConv`); the
address of such a function is a closure that converts. Where the width
is the function's meaning, there is a version of it: `strtol` and
`strtoul` (long's range and `ERANGE`), `ldiv` (its result's layout).
`printf`'s and `scanf`'s `l`, `z` and `t` are `long`'s size, `ll` and
`j` 8 bytes.

**internal/c23 with 4-byte words**: a `Ptr` in a register is as it was;
in memory a pointer is one word, so a tinfo's kinds, the side tables'
keys, `Memmove`'s, `Memset`'s and `LoadPtr`'s pointer words are
`wordSize` (4) bytes (`model.go`), C's object header is four words (16
bytes), and the marker of an over-aligned object two. The tag of an
out-of-bounds pointer is bit 31 with split, as before. Go strings are
words C may read and not write, inline or not: c23 never looks inside
one; `C.CString` and `C.GoString` copy bytes.

**Go's side**: `C.long`, `C.ulong`, `C.size_t`, `C.uintptr_t` are 4
bytes; a Go struct passed to C and a C struct read by Go have one layout
(the interop test, which pokes at word indexes computed from the types
and expects the sizes of its target's word).

**Measured** (`go test cmd/cc` and the suites, `GOWASMGC_POISON=1`):
the suites run for js from a test binary built for the host with

pointer memory with split (the tag), whatever the word size.

## What it does not do yet

- **Go's fault on a tagged word is fatal** natively, and a trap with
  GOWASM=gc,split (on linear wasm it is a panic) (`unexpected fault address
  0x0`): the kernel reports a non-canonical address as `SI_KERNEL` with no
  address, which `sigpanic` does not turn into a panic. Safe, but the demo
  needs `debug.SetPanicOnFault`. The runtime could treat that fault in Go
  code as `panicmem`.
- **The tag is bit 55 (31 with split), which not every target can use**:
  32-bit targets have no bit 55, and LA57, s390x and amd64's LAM treat
  it differently.
- **The side tables** are maps under a mutex (a list, for a stack); an
  array of capabilities per word would be faster. Each pointer load from
  Go's memory looks for a table.
- **Storing a local's address always moves the local to the heap**, even
  into another local, where Go itself would keep both on the stack:
  `StorePtr` is opaque to escape analysis. Lowering into SSA fixes it.
- **Every access is a call** that reads type tables, and each pointer
  load and store asks the heap for C's object; nothing is eliminated
  statically yet (most stores' types are known, as in CCured). Each C
  object has a 24-byte header.
- **cc's output is not in the build cache's key**: the action ID has the
  package's files, but not cc itself, so after changing cmd/cc, clean the
  cache (`go clean -cache`).
- **Language and library:** the gaps are what slimcc's tests show
  (below): `_BitInt`, `_Complex`, inline assembly, `__int128`, vector
  types, `static_assert` used as an expression, a `long double` with more
  than a double's precision, local arrays aligned to 16 as on x86-64 (only
  `_Alignas` objects are over-aligned, in the heap). Go cannot call a
  variadic C function. A pointer made from an integer has no capability,
  by design (`(int *)(long)&x` cannot be used), but for one kept in an
  `intptr_t` or a `uintptr_t`.
- **`free` returns no memory, and finds no use after free or double
  free.** A pointer still kept in live memory after its object is freed
  keeps the object, and what it points to, alive: 256 freed 1 MiB buffers
  whose pointers stay in a global keep 259 MiB resident, where musl's
  `free` gives them back. Fil-C's collector repoints such pointers at a
  freed singleton, keeping their address, so the memory comes back at the
  next collection; here the collector would tag the stale words in C's
  objects as it marks, and keep each freed object one more cycle (Go scans
  each stack only once).

## C23, and how much of it

The frontend (cmd/cc/internal/ccmain) has a full C23 preprocessor
(`pp.go`: macros disabled as GCC disables them, `#embed`, `__has_include`,
`__VA_OPT__`; `TestPreprocessGCC` compares it with `gcc -E`) and a parser
that types everything as it parses (`types.go`, `ast.go`, `parse.go`,
`expr.go`, `stmt.go`, `init.go`): every declarator, bit-fields, designated
initializers by C's current object, compound literals with storage
classes, `_Generic`, `typeof`, `auto`, `constexpr`, `nullptr`, VLAs, and
the GNU extensions slimcc tests (statement expressions, case ranges,
labels as values, local labels, `cleanup`, `__attribute__`), and C2y's
`defer`, named `break`/`continue`, declarations in conditions, `_Countof`
and delimited escapes.

The generator hoists every local to the top of its function, so `goto`
works; a function Go's structured statements cannot hold (a `goto` into a
block, a case label nested in a statement, labels as values, `setjmp`) is
generated flat, as labels and gotos. Struct values live in memory (a
struct rvalue is its `c23.Ptr`; the callee copies its parameters; results
are written where the caller says). Function pointers point to
`c23.Func` objects, and a call through one checks the function's Go type
(adapting it for a function without a prototype). Variable arguments are
`...any`, and a `va_list` is a `c23.VaList` object.

`setjmp` and `longjmp` work as in Fil-C: `longjmp` may only return to a
function still running, which is checked. A function that calls `setjmp`
runs its body in a closure that recovers `longjmp`'s panic and jumps back
to the `setjmp`'s site. A C thread is a goroutine (`pthread.h`, and
`threads.h` on the same machinery, so `__STDC_NO_THREADS__` is not
defined); a `_Thread_local` object is each goroutine's, made on first use; `_Atomic`
objects and `stdatomic.h` use `sync/atomic`, or a lock for small objects
and pointers.

Sockets (`sys/socket.h`, `netinet/in.h`, `arpa/inet.h`, `netdb.h`,
`sys/un.h`) are `net`'s listeners and connections, in
internal/c23/sys/socket (and netdb, arpa/inet, netinet/in, net/if; only
sys/socket, netdb and net/if link `net`). They are descriptors of internal/c23's table, as files are, so
`read`, `write`, `close`, `dup`, `fdopen` and `fcntl`'s `O_NONBLOCK` work
on them. Go has no readiness, so `poll` and `select` have one of their
own: a descriptor whose reads may block (a socket's connection, a pipe, a
terminal) is read ahead by a goroutine into a buffer of up to 64 KiB, and
is readable when that has data or an end; a listener accepts into a
queue, a datagram socket receives into one. Non-blocking `connect` dials
in the background (`EINPROGRESS`, then `POLLOUT` and `SO_ERROR`). Writes
block until Go has written. Names resolve with Go's resolver;
`getnameinfo` gives a port's number, not its name. Not there: ancillary
data (`SCM_RIGHTS`), raw sockets, `AF_UNIX` datagrams, and options Go
cannot set (kept for `getsockopt`, otherwise ignored).

`ndbm.h`'s databases are file.pag, a log of stores and deletes that
`dbm_open` reads and `dbm_close` rewrites compactly (and file.dir,
empty), their keys in sorted order: a format of cmd/cc's own, which
POSIX leaves to the library. `posix_devctl` is `ioctl` returning the
error number; `ppoll` does not change the signal mask while it waits.

Files and the system: `statvfs` and `statfs` are the system's where
package syscall has them (Linux, macOS, the BSDs; `ENOSYS` elsewhere,
Windows and wasm included); `nftw` walks with `os.ReadDir` (names in
order); `wordexp` expands in Go as glibc does, running `/bin/sh` only
for a command substitution; `times`, `sysinfo` and `getifaddrs` give
what Go and `/proc` know; `libintl.h` has no catalogs (messages are
their own translations) and `catopen` none either; `res_query` cannot
give raw DNS messages (Go's resolver has none).

The rest of POSIX's files and system interfaces (musl's headers in POSIX
mode; `TestPxFiles`): the `*at` functions resolve a name relative to a
directory descriptor against that directory's name (made absolute when
it was opened, so `fchdir` does not move it), not with `os.Root`, which
would keep names inside the directory; a directory renamed after it was
opened is not followed, and `futimens` and `fexecve` use the name a
file was opened by. `AT_SYMLINK_NOFOLLOW` sets a link's own times only
on Linux, `AT_EACCESS` checks the effective ids only on Linux, and
`mkfifo` and `mknod` are the system's where package syscall has them
(`ENOSYS` elsewhere). `fdopendir`'s `DIR` reads by name too, and
`posix_getdents` returns readdir's entries (sorted, read at its first
call; `lseek` does not rewind it). `pipe2`'s `O_NONBLOCK` pipe is read
ahead, as a pipe that `poll` watches: what the program writes to it may
not be readable at once. `pathconf` gives Linux's limits whatever the
file system (glibc's `_PC_LINK_MAX` of 127 for all), `confstr` only
`_CS_PATH` and the width-restricted environments; `getlogin` is
`$LOGNAME` (musl's), `gethostid` `/etc/hostid` or 0; `ttyname` reads
`/proc/self/fd` on Linux, else searches `/dev`. The ids, `nice` and
priorities, `getrlimit` and `setrlimit` are the system's on Linux, macOS
and the BSDs (Go raises `RLIMIT_NOFILE` at start, so that one is not
what the program started with); elsewhere ids may only be set to what
they are, there are no limits, and `setrlimit` fails with `EPERM`.
`flockfile` is a recursive lock per `FILE` that the streams' functions
do not take, so the `_unlocked` ones are theirs. `mlock` and its kin
succeed and do nothing; `shm_open` opens a file of `/dev/shm` (the
temporary directory elsewhere), whose `MAP_SHARED` mappings the process
shares with itself only. `getpwent` and `getgrent` read `/etc/passwd` and
`/etc/group`; `utmpx.h` reads glibc's x86-64 records of `/var/run/utmp`
(none elsewhere) and cannot write (`pututxline` fails with `EPERM`).
netdb.h's databases are `/etc/hosts`, `/etc/networks`, `/etc/protocols`
(else getprotobyname's table) and `/etc/services` (else the few services
Go's net package knows without one); `if_nameindex` is
`net.Interfaces`. Pseudo-terminals (`posix_openpt`, `grantpt`,
`unlockpt`, `ptsname`) are the system's on Linux and macOS (`ENOSYS`
elsewhere), as are `tcgetwinsize` and `tcsetwinsize`; `_Fork` fails as
`fork` does.

Locales: the library has "C" (or "POSIX") and "C.UTF-8" (or "C.utf8"),
which behave alike (C's multibyte characters are UTF-8's already);
`newlocale` fails with `ENOENT` for any other name, as glibc does for a
locale it has not installed (musl accepts any name), and `""` is the
environment's, or C's. A `locale_t` says which categories are C.UTF-8's;
`uselocale` keeps one for each thread. The `_l` functions are the plain
ones, whatever the locale. `wcwidth` is glibc's in a UTF-8 locale, from
Unicode 15.1's East Asian widths (a table, as Go's unicode has none) and
Go's tables of marks and format characters. `random` and `rand_r` are
glibc's (musl's numbers differ), `a64l` sign-extends as POSIX says,
`crypt` has MD5-, SHA-256- and SHA-512-crypt and DES (not bcrypt or
yescrypt), `strptime` is glibc's in the C locale (`%z` and `%Z` are read
and dropped: `struct tm` has no `tm_gmtoff`), and `inet_network`,
`inet_lnaof` and `inet_makeaddr` are glibc's (musl's are not in the
network's byte order). `tzset`, and `localtime` when `TZ` changes, read
`TZ` as a zone's name (Go's `time.LoadLocation`) or as a POSIX TZ string
(Go's reading of a zone file's footer); `tzname`, `timezone` and
`daylight` are this year's. `mbsnrtowcs` leaves a character its limit
splits for the next call, rather than keeping its bytes in the
`mbstate_t`, and `open_wmemstream`'s positions count wide characters.
`strerror_r` is POSIX's, returning a number, unless `_GNU_SOURCE` is
defined.

`regex.h` is a matcher of its own (internal/c23/regex), not Go's
`regexp`: POSIX's basic and extended syntax with glibc's GNU operators
and error codes, back-references in both, and the leftmost-longest match
with each subexpression, from the left, the longest it can be. It works
on sets of positions, so it takes polynomial time where there are no
back-references (and backtracks where there are). `termios.h` is the
terminal's on Linux (with the generic termios: not mips, ppc64) and
macOS (translated to and from its struct and flags), with Linux's
struct and constants; elsewhere no descriptor is a terminal (`ENOTTY`).

Linux's event descriptors are descriptors of the same kind, on every
target: `epoll` (internal/c23/sys/epoll) finds its interests ready with
`poll`'s readiness, level-triggered, or with `EPOLLET` when something
became ready or arrived (data read ahead, an `eventfd` write, a timer's
expiry) since it last reported them, and `EPOLLONESHOT`; an epoll
descriptor is itself pollable. `struct epoll_event` is 16 bytes
everywhere: Linux packs it on x86-64 (12 bytes), where `epoll_data`'s
pointer would be unaligned, and an unaligned pointer cannot keep its
capability. `eventfd` is a counter, `timerfd` a `time.Timer` (on Go's
monotonic clock, also for `CLOCK_REALTIME`), and `signalfd` reads the
signals of its mask pending for the reading thread or the process, as
`sigwait` takes them. `setitimer`'s three timers count wall time;
`ITIMER_REAL` is `alarm`'s. `wait4` gives a child's times (and the rest
of `struct rusage` where the system has it); `waitid` reports only ends,
and `P_PGID` is any child. `sigqueue` carries its value only to the
program's own process, and signals are not queued (one pending is sent
once). `pthread_kill` of another thread that does not block the signal
runs the handler on a goroutine of its own, as the program's other
signals; `sigaltstack` and `siginterrupt` are kept and change nothing.

Interprocess communication is the process's own. C's memory is Go's
heap, which no other process can map, and the program's other processes
are programs it spawns, so POSIX message queues (`mqueue.h`,
internal/c23/mqueue), XSI message queues, semaphore sets and shared
memory segments (`sys/msg.h`, `sys/sem.h`, `sys/shm.h`) live within the
process, shared by its threads, by name or key as on Linux (and with
Linux's structures, limits and errors); a spawned program does not see
them. A message queue descriptor is a descriptor of the table, which
`poll`, `select` and `epoll` see (readable when a message waits, writable
when the queue is not full); `mq_notify` signals with `SI_MESGQ` and the
registered value, or calls the function on a new thread. `shmat` returns
a pointer to one C object of the segment's size, the same for every
attach, and cannot place a segment at an address; `SHM_RDONLY` attaches
it writable. `SEM_UNDO`'s adjustments are applied by `exit`, after the
`atexit` functions, where only the threads still running see them.
`ftok` is glibc's formula. `aio.h` (internal/c23/aio) runs each operation
on a goroutine, those of one descriptor in order as glibc does, with
`pread` and `pwrite` (or `read` and `write` where there is no offset),
and notifies as the `struct sigevent` says (`SI_ASYNCIO`); `aio_cancel`
cancels only what has not started. `shm_open` is `sys/mman.h`'s.

POSIX's threads are complete (internal/c23/pthread, and internal/c23's
`cancel.go`): attributes (`pthread_create` honors the detach state and
an explicit scheduling; the stack's size and address, the guard and the
scope are kept for the getters, as a goroutine's stack grows),
read-write locks (readers preferred, as glibc's default), barriers, spin
locks (an `int`, spinning then yielding), robust mutexes (a thread that
ends holding one gives `EOWNERDEAD` to the next to lock it, and an
unlock without `pthread_mutex_consistent` makes it `ENOTRECOVERABLE`),
condition variables on `CLOCK_MONOTONIC`, and cancellation with musl's
`pthread_cleanup_push` (a `struct __ptcb` per block; the handlers are
the thread's, in Go). A canceled thread acts at the cancellation points
that wait (`pthread_join`, `pthread_cond_wait` and `timedwait`,
`sleep`, `usleep`, `nanosleep`, `clock_nanosleep`, `sem_wait`,
`sigwait` and its kin, `sigsuspend`, `pause`, `poll`, `select`,
`epoll_wait`), at `pthread_testcancel`, and when `read` or `write` is
called (not while it waits): it runs its cleanup handlers, the last
pushed first, then its keys' destructors, and ends with
`PTHREAD_CANCELED` (which is not `(void *)-1` but -1 without bits 31
and 55: a pointer without a capability stored in Go's memory loses the
tag, so -1 would not compare equal once stored). Asynchronous cancellation acts at the same points
(and when it is chosen): a goroutine cannot be interrupted. Cancellation
and `pthread_exit` of the main thread wait for the other threads, then
exit with status 0. Scheduling changes nothing: policies and priorities
are kept, as for a user without privileges (a real-time policy is
`EPERM`; `sched_setscheduler` and `sched_setparam` behave as glibc's,
not musl's `ENOSYS`), and `sched_rr_get_interval` is 100 ms;
`pthread_setconcurrency` keeps its level (musl's is `EAGAIN` above 0);
`pthread_atfork` keeps its handlers and never calls them. The CPU-time
clocks (`CLOCK_PROCESS_CPUTIME_ID`, `CLOCK_THREAD_CPUTIME_ID`,
`clock_getcpuclockid`'s and `pthread_getcpuclockid`'s, encoded as
Linux's) count the time since the process or the thread started: Go
cannot know a goroutine's processor time. `timer_create`'s timers are
`time.Timer`s on Go's monotonic clock, for every clock (an absolute
`CLOCK_REALTIME` time is converted when the timer is set); a
`SIGEV_SIGNAL` expiry is a process signal with `SI_TIMER` and the
`sigev_value`, and an expiry while it is pending is an overrun (signals
are not queued, so two timers of one signal share it); `SIGEV_THREAD`
calls the function on a new detached thread; `struct sigevent` is
glibc's. `clock_settime` is `EPERM`
and `clock_getcpuclockid` of another process `EPERM`. `killpg` signals
the program's children in the group (their group is the system's where
package syscall has `Getpgid`) and the program itself if the group is
its own. `psiginfo` writes glibc's text, `sigpause` is XSI's, and
`sigsetjmp(env, 1)` saves the mask in `env`, which `siglongjmp` (and
`longjmp`, as in glibc and musl) restores.

C's library is Go: internal/c23, the run-time support of the generated
Go (memory and capabilities, errno, descriptors, threads' storage, the
floating-point environment), and a package for each header with
functions, named after it: internal/c23/stdio, internal/c23/sys/socket
and so on (a function that more than one header declares is in the
first's). The generated Go imports internal/c23 and the packages whose
functions it calls (libcpkg.go), so a program links only the library it
uses; cmd/go lists them all as the dependencies of a package it builds
with cmd/cc, and the linker takes only those imported. A header's
helpers are in its package, those that two need in internal/c23.

The C prototypes are in the headers cmd/cc provides (`headers.go`,
`headers_*.go`); `TestLibc` and its kin compare the library with gcc's.

`go test cmd/cc -run Slimcc` runs slimcc's tests (MIT, C23 and GNU C);
`testdata/slimcc/status.txt` lists the 81 of 106 that pass. Given
checkouts, `-run CTestsuite -ctestsuite DIR` runs c-testsuite (all 220
single-exec tests pass) and `-run Torture -torture DIR` GCC's
`gcc.c-torture/execute` (1467 of the 1576 that gcc passes); neither is
vendored, as their licenses are not MIT, but `testdata/*.status` list what
passes. Most of the torture tests that fail use inline assembly or vector
types, or keep pointers in integers.

Real programs: Lua 5.4 and SQLite 3.46.1 (the amalgamation and its
shell) translate, build and run unmodified, with only the headers cmd/cc
provides; Lua passes its test suite's files, and SQLite gives the same
output as when gcc builds it. Both run 20 to 40 times slower than
native: every access is a call, and a pointer in untyped memory (a
union's, malloc's) goes through a side table.

Complex numbers are Go's complex64 and complex128 (`complex.h` is
`math/cmplx`); `_BitInt(N)` goes to 64 bits (`BITINT_MAXWIDTH`, the least
C23 allows); GNU's nested functions are Go closures (still valid after
their parent returns, unlike GCC's trampolines).

Floating point is Go's: IEC 60559's binary32 and binary64 (`long double`
is `double`), rounding to nearest. On amd64 and arm64 cmd/cc also has
Annex F's environment, and claims it (`__STDC_IEC_559__`,
`__STDC_IEC_60559_BFP__`): each thread has a rounding direction and
exception flags (internal/c23's `fenv.go`), and code under
`#pragma STDC FENV_ACCESS ON` or C23's `FENV_ROUND` calls helpers for its
arithmetic, conversions and relational comparisons, each of which runs its
one instruction in the direction asked and collects the flags it raises
(`fenv_amd64.s`, `fenv_arm64.s`). Go's ABI fixes the hardware's direction
at every call, so the environment cannot stay in MXCSR or FPCR between
operations. Other code is Go's arithmetic, as C lets it assume the default
environment there. The library follows the environment: `sqrt`, `fma`,
the `rint` family, C23's narrowing `fadd` family (rounded once, to odd
then to float) and `printf`/`strtod` honor the direction, and the math
functions raise Annex F's exceptions as well as setting `errno`.
`FP_CONTRACT OFF` keeps Go from fusing a product into an addition.
`TestFenv` compares it all with gcc's in the four directions. Wasm has no
rounding directions or flags: there `fenv.h` has only `FE_TONEAREST`, and
Annex F is not claimed.
