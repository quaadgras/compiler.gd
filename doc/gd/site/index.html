gd compiler

A compiler for Go that aggressively allocates on the stack. Intended to reduce GC pressure in real-time graphics, and to let carefully designed programs run without a GC.

−59%time for calls through closures and interfaces (1 allocation → 0)
16 Binline storage in every interface
15 Bstrings stored without allocating

What's different?

  1. Interfaces include 16 bytes of inline storage (strings and slices both fit).
  2. Small string optimization (15 bytes stored without allocating or a hash).
  3. Escape analysis for dynamic dispatch (closures and interfaces).
  4. Pointer results can be allocated on the caller's stack (if they don't escape).
  5. The entire compiler and standard library in a single self-contained binary.
  6. Small wasm/js binaries: about 400 KB for a fmt hello world, no dispatch loop.

Not everything is faster: wider interfaces and strings cost more to copy, and some benchmarks (encoding/json decoding) are slower. Full results in doc/gd.

Does it work?

The language and standard library test suites pass on amd64, arm64 and js/wasm.

Try it

In your browser: the playground. Or build it:

git clone https://github.com/quaadgras/compiler.gd
cd compiler.gd/src && ./make.bash
export PATH=$PWD/../bin:$PATH

The ABI differs from stock Go (wider interfaces and strings), so assembly and unsafe code that relies on their layout needs care.

How? Why?

@Splizard, the project's director, developed an interest (after 10 years of Go) in exploring what an alternative Go compiler could look like. Recent technology has made an endeavour of this scale far more accessible. The compiler is intended to support graphics.gd.
